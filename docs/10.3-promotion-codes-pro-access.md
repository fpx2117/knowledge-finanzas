# Promotion Codes & Temporary Pro Access

## 1. Objetivo

Este documento define el sistema de códigos promocionales de la plataforma.

Los códigos promocionales permiten otorgar:

```text
PRO access
```

por un período configurable sin requerir una suscripción paga mediante Mercado Pago.

Ejemplos:

```text
BETA30
→ 30 días de Pro

EARLYUSER90
→ 90 días de Pro

PARTNER180
→ 180 días de Pro

TEST7
→ 7 días de Pro
```

Principio central:

```text
Promotional Pro Access
≠
Paid Subscription
```

Y:

```text
Promotion Code
≠
Mercado Pago Discount Code
```

---

# 2. Alcance

El sistema debe permitir:

```text
crear códigos promocionales

configurar duración

configurar período de validez

configurar cantidad máxima de usos

configurar usos por usuario

activar/desactivar códigos

revocar códigos

redimir códigos

otorgar Pro temporal

auditar redenciones

consultar promociones activas
```

---

# 3. Casos de uso

Ejemplos:

```text
beta testers

early adopters

influencers

partners

support compensation

marketing campaigns

launch promotions

internal testing

giveaways

customer recovery campaigns
```

---

# 4. Modelo de acceso

El modelo de producto existente es:

```text
TRIAL

PRO

EXPIRED_READ_ONLY
```

Los códigos promocionales agregan una nueva fuente de acceso Pro:

```text
PAID PRO
or
PROMOTIONAL PRO
```

Ambos resuelven finalmente a:

```text
EffectiveProductAccess = PRO
```

---

# 5. Important Separation

Mantener:

```text
Billing Subscription
≠
Promotional Grant
```

Una promoción nunca debe crear:

```text
fake Mercado Pago subscription
```

ni modificar falsamente:

```text
billing_subscriptions.status = ACTIVE
```

---

# 6. Product Access Resolution

Actualizar conceptualmente:

```text
if effective paid Pro subscription:
    PRO

else if active promotional Pro grant:
    PRO

else if active trial:
    TRIAL

else:
    EXPIRED_READ_ONLY
```

---

# 7. Promotional Access Source

Aunque ambos resuelvan a `PRO`, debe mantenerse información de origen.

Ejemplo:

```text
accessState:

accessSource:
PROMOTION
```

o:

```text
accessState:
PRO

accessSource:
SUBSCRIPTION
```

# 10. Code

Ejemplos:

```text

LAUNCH2026

PARTNER90
```

Recomendación:



```text
BETA30
```


---

# 12. Promotion Status

Estados:

```text
DRAFT

ACTIVE

PAUSED

EXPIRED

REVOKED
```

---

# 13. DRAFT

Código creado pero todavía no disponible.

---

# 14. ACTIVE

Puede ser redimido si cumple todas las demás reglas.

---

# 15. PAUSED

No acepta nuevas redenciones.

Las promociones ya otorgadas continúan según su política.

---

# 16. EXPIRED

La ventana de redención terminó.

No afecta grants ya otorgados.

---

# 17. REVOKED

Código retirado permanentemente para nuevas redenciones.

La revocación de grants existentes debe ser una acción separada.

---

# 18. Duration

Ejemplos:




```text

→ 7 days
```

# 23. Duration Must Not Be Hardcoded

Incorrecto:

```ts
if (code === "BETA30") {
  addDays(30)
}
```

```text

↓
durationValue
↓
PromotionService
```

```text
how long the code can be redeemed
```

```text

```

```text

Redeemable:
August 1–31

90 days
```

# 39. Promotion Redemption Flow

```text
User enters code
↓
Normalize code
↓
Load PromotionCode
↓
Validate status
↓
Validate redemption window
↓
Validate global usage limit
↓
Validate user usage limit
↓
Validate stacking policy
↓
Create Redemption
↓
Create Promotional Access Grant
↓
Commit
↓
EffectiveProductAccess = PRO
```

---

# 40. Atomic Redemption

Validación y creación deben ejecutarse atómicamente.

Evitar:

```text

99 currently used

10 simultaneous requests
```

que terminen en:

```text
109 redemptions
```

# 47. Why Promotion Overrides Trial

Porque:

```text

```

```text

```

según política Pro.


```text

```

# 57. Promotion Expiration


# 200. Final Product Rule

Los códigos promocionales deben permitir otorgar acceso Pro de forma controlada y flexible sin alterar la realidad de billing.

La regla es:

```text
PROMOTION CODE
↓
VALIDATION
↓
REDEMPTION
↓
PROMOTIONAL ACCESS GRANT
↓
PRO ACCESS
↓
EXPIRATION
↓
NORMAL ACCESS RESOLUTION
```

Nunca:

```text
PROMO CODE
↓
fake Mercado Pago subscription
```

El tiempo, cantidad de usos, período de redención y allowances deben ser configurables.

Los términos otorgados a un usuario deben quedar congelados al momento de redención para mantener trazabilidad y evitar cambios retroactivos inesperados.
